# PSEdit — 한·일 문서 작성·윤문

목표는 하나다: 독자가 첫 화면에서 **결론 / 고를 것 / 할 일**을 안다. 장황함·반복·AI 문체 제거는 그다음이다. 구조 → 문체 순서를 절대 바꾸지 않는다.

## 1. 모드 판별

| 요청 | 모드 | 절차 |
|---|---|---|
| 새 문서를 쓴다 | 작성 | 3절 |
| 기존 문서·붙여 넣은 글을 다듬는다 (윤문, 퇴고, 교정, ブラッシュアップ, 推敲, リライト) | 윤문 | 4절 |
| 같은 문서를 다른 상세도·다른 언어로 만든다 | 판본 변환 | 5절 |

## 2. 공통 규칙

### 불변식 (모든 모드)
- 원문·사용자 제공 자료에 없는 사실·숫자·고유명사를 만들지 않는다.
- 숫자·인용을 지우거나 바꾸지 않는다. 부정·조건·시제·확실도·단위를 바꾸지 않는다 (뜻 뒤집기 금지).
- 코드 블록과 표 안의 데이터를 바꾸지 않는다.
- **판단과 사실을 구분한다.** 주어진 사실로 추천·결론을 내리는 것은 판단이지 지어내기가 아니다. 작성 모드에서는 반드시 판단해서 추천한다 (정보가 부족하면 "A를 추천. 단, X이면 B"처럼 조건부로). `[확인 필요: …]` / `【要確認：…】`는 문서가 성립하지 않을 만큼 빠진 **사실**에만 쓴다. 요청받지 않은 항목(담당자 이름 등)을 채우려고 쓰지 않는다.
- 윤문 모드에서 원문에 결론이 없으면 결론은 저자의 몫이므로 넣지 않는다 (4절).
- 규칙끼리 부딪히면: 사용자의 이번 지시 > 불변식 > 취향 규칙(6절) > 템플릿·패턴 사전.

### 문서 종류 → 템플릿
| 요청 표현 | 템플릿 |
|---|---|
| 설계서, 아키텍처, 기술명세서, 기술 사양서, 設計書, 方式設計, 技術仕様書 | `design` |
| 검토자료, 비교, 선정, 제안, 検討資料, 提案書 | `review` |
| 조사자료, 리서치, 분석, 調査資料, 調査報告 | `research` |
| 사용자설명서, 매뉴얼, 가이드, 利用者マニュアル, 手順書 | `manual` |
| 작업보고, 진행·완료 보고, 作業報告, 進捗報告 | `report` |
| 회의록, 議事録 | `minutes` |

「보고서」만 있으면 내용으로 고른다: 결정을 구하면 `review`, 발견을 전하면 `research`, 진행 상황이면 `report`. 그래도 모르겠으면 가장 가까운 것을 고르고 어떤 템플릿을 썼는지 한 줄로 알린다.

### 기술 스택을 다룰 때
기술명세서를 쓰거나, 문서가 기술을 3개 이상 다루거나, `detailed` 세션 설명에서 기술 스택을 설명하면 사용자가 요청하지 않아도 `references/tech-stack.md`를 읽고 **① 구성도 → ② 기술별 역할 표 → ③ 연동 흐름**을 만든다.
- 그리기 전에 출력 형식(Markdown+Mermaid / HTML+SVG)을 정한다. 사용자 지정·기존 파일·프로젝트 관례로 정해지지 않으면 추천을 붙여 한 번 묻는다 (tech-stack.md 6절).
- 기술 이름·버전·용도·경로는 의존성 파일과 코드에서 확인한 것만 쓴다.
- 윤문 모드에서는 그림을 직접 넣지 않고 결과 보고에서 제안만 한다.

### 사용자설명서에 화면 조작이 있을 때
`manual`의 절차에 화면 조작이 있으면 사용자가 요청하지 않아도 `references/manual-screens.md`를 읽고 **화면 이미지 + 번호표 + 같은 번호의 동작 목록**으로 쓴다.
- 이미지는 사용자·저장소의 캡처 → 직접 캡처 → 재현 이미지(HTML로 비슷하게 만들어 PNG로 렌더링) 순서로 구한다. 재현 이미지는 캡션에 표시하고, 재료에 없는 버튼·메뉴를 그리지 않는다.
- 형식은 따로 정해지지 않으면 HTML(번호표를 CSS로 겹침). 묻지 않고 한 줄로 알린다. 장이 4개 이상이면 왼쪽 고정 목차와 제목 띠로 짠다.
- 문장은 한 번호에 한 동작, 한 문장. 위치는 번호표가 보여 주므로 쓰지 않는다.
- 번호표 위치는 렌더링 결과를 직접 보고 확인한다.

### 다른 문서 표준이 있을 때 (우선순위)
프로젝트에 자체 템플릿·문서 표준이 있으면 **그쪽 구조가 이긴다** (예: `_TEMPLATE/` 같은 템플릿 폴더, 프로젝트 CLAUDE.md가 정한 양식). 이때 PSEdit은 템플릿을 덮어쓰지 않고 다음만 적용한다.
- 그 양식의 첫 섹션 또는 첫 문단에 결론이 오게 한다 (섹션을 새로 만들 수 없으면 첫 문단으로).
- `references/structure-checklist.md`의 B·D·F와 문체 점검.

### 언어
- 새 문서: 사용자가 지정한 언어. 지정이 없으면 요청 언어. 팀 공유용이라고 하면 일본어.
- 윤문: 원문 언어. 한·일이 섞여 있으면 많은 쪽을 주 언어로 하고, 인용된 다른 언어 부분은 건드리지 않는다.
- 용어 풀이 방식(괄호 병기 등)은 전역·프로젝트의 용어 규칙이 있으면 그것을 따른다.

### 상세도 3단계
| 단계 | 바꾸는 표현 (한 / 日) | 세션 설명 | 문서 |
|---|---|---|---|
| 요약 `short` | 짧게, 간단히, 한 줄로, 요약해서 설명 / 短く, 簡潔に, 要点だけ | 결론 + 이유 1줄 + 할 일. 3~5줄 | 결론·결정 필요·근거(항목당 1줄). 상세 생략 |
| 보통 `normal` | 보통으로, 기본 상세도로 / 普通で, 標準の詳しさで | 결론 + 근거 2~3개 + 할 일. 한 화면 이내 | 골격 전체. 상세는 핵심만 |
| 자세히 `detailed` | 자세히, 구체적으로, 상세히 / 詳しく, 具体的に, 詳細に | 결론 먼저, 이어서 단계별 설명·예시·코드·주의점 | 골격 전체 + 예시·절차·수치·대안별 장단점·리스크 대응 |

- **표현이 "어떻게 답할지"를 꾸밀 때만 단계를 바꾼다.** "회의록을 요약해 줘"의 「요약」은 작업 내용이지 상세도 지정이 아니다. 「보통」「기본」「標準」 같은 낱말이 문장에 있다는 것만으로 바꾸지 않는다.
- 우선순위: 이번 요청의 지정 > 문서 frontmatter `detail` > 이 세션에서 마지막으로 지정한 단계 > 기본값(세션 설명 `short`, 문서 `normal`).
- 지정은 다음 지정 전까지 이 세션에 유지한다. 파일로 저장하는 문서에 대해 지정하면 frontmatter에 `detail: <단계>`를 기록한다 (대화 안에서만 내는 글에는 기록하지 않는다). 프로젝트 양식이 frontmatter를 쓰지 않으면 기록하지 않고 그렇게 알린다.
- 어느 단계든 결론이 맨 앞이다. `detailed`는 깊이를 더하는 것이지 같은 말을 늘리는 것이 아니다. 깊이를 더하는 수단은 `references/communication-principles.md` 「자세히」 항목을 따른다.
- 이 상세도는 분량과 구성만 정한다. 용어 풀이의 깊이는 용어집 설정 등 별도 규칙을 따른다.

### 독자
frontmatter `audience: self | team | stakeholder | end-user`. 없으면 종류로 추정한다 (design=team, review=stakeholder, manual=end-user, 나머지=team).
- `stakeholder`, `end-user`: 전문 용어는 처음 나올 때 한 줄로 푼다. 수치에는 "그래서 좋은지 나쁜지"를 붙인다.
- `self`, `team`: 이미 공유된 용어는 풀지 않는다.

## 3. 작성 절차

1. 종류·언어·상세도·독자를 정하고, 프로젝트 문서 표준이 있는지 확인한다 (2절). 확인 방법: 프로젝트 `CLAUDE.md`·`.claude/rules/`에 문서 양식 지시가 있는지, 쓰려는 위치 근처에 `_TEMPLATE*`·템플릿 폴더나 같은 종류의 기존 문서가 있는지 본다.
2. `templates/{ko|ja}/{type}.md`를 읽고 그 순서로 쓴다. 섹션 순서: 결론 → 결정 필요 → 배경 → 근거 → 선택지 비교 → 상세 → 리스크·미확인 사항. 해당 없는 섹션과 `<!-- -->` 안내 주석은 지운다.
3. `references/structure-checklist.md`로 구조를 점검한다. A·B가 통과할 때까지 고친다.
4. `references/patterns-{ko|ja}.md`로 문체를 점검한다.
5. 취향 규칙(6절)을 적용한다.
6. 마무리 요약을 붙이지 않는다. 사용자에게는 무엇을 만들었는지와 「결정 필요」 항목만 짧게 알린다.

작성 시 세부 규칙
- 같은 사실을 결론·근거·표에 거듭 쓰지 않는다. 표가 있으면 근거는 표에 없는 것만 쓴다.
- "다음 달 말" 같은 상대 날짜는 오늘 날짜를 기준으로 절대 날짜로 쓴다 (예: 2026-12-31).
- 결론 3줄에는 풀이가 필요한 전문 용어를 쓰지 않는다. 쉬운 말로 쓰고, 용어는 근거·상세에서 처음 나올 때 푼다.

## 4. 윤문 절차

윤문의 원칙은 **사용자의 글을 사용자의 글로 남기는 것**이다.

고치는 범위는 비율이 아니라 **정보가 보존되는가**로 정한다. 사실·숫자·조건은 하나도 잃지 않고, 저자의 말투(경어·평어, 敬体·常体, 즐겨 쓰는 표현)는 패턴 사전에 걸리지 않는 한 그대로 둔다.

1. 전체를 읽고 종류·언어를 판별한다. 템플릿을 통째로 씌우지 않는다.
2. **구조**
   - 결론이 원문 어딘가에 있으면 맨 앞으로 옮긴다. 옮길 때 확실도는 원문 그대로다. 원문이 추측으로 쓴 결론("~로 보인다", "〜ではないでしょうか")은 결론 섹션에서도 추측 하나를 남긴다 (불변식이 구조 규칙보다 앞선다).
   - 결론이 원문에 없으면 본문에 넣지 않는다. 고친 글은 그대로 내고, 보고(6단계)에서 원문 사실로 만들 수 있는 결론 후보 2~3개를 추천과 함께 제시한다. 사용자가 고르면 그때 넣는다.
   - 원문에 흩어진 선택지·결정 사항은 「결정 필요」/「要判断」으로 모은다. 원문에 추천이 없으면 질문만 쓰고 추천·기한 칸을 만들지 않는다.
3. **빈 문장과 반복 삭제**: 내용 없는 첫머리·맺음·메타 발화(patterns 2절)와 같은 말의 되풀이를 지운다. 반복은 정보가 더 많은 쪽을 남기고, 지우는 쪽에만 있던 숫자·조건은 남기는 쪽으로 옮긴다.
4. **문체**: `references/patterns-{ko|ja}.md`의 수정 순서(입장 → 주체 → 구조 → 어휘 → 기호)로 고친다.
5. 취향 규칙(6절)을 적용한다.
6. 결과 보고. 파일이면 파일을 고치고, 붙여 넣은 글이면 고친 글 전체를 낸 뒤 아래를 원문 언어로 붙인다.
   ```
   구조 / 構成: {옮기거나 모으거나 지운 것 한 줄}
   문체 / 文体: {고친 문장 수}/{전체 문장 수}
   결론 후보 / 結論の候補: {원문에 결론이 없을 때만. 추천 표시}
   확인 필요 / 要確認: {원문만으로는 알 수 없는 사실. 없으면 줄 삭제}
   ```
   고친 문장 수는 한 문장을 한 번만 센다. 패턴이 여럿 걸리면 주된 하나로 분류하고, 패턴 사전에 없는 문법 오류(주술 호응 등)는 「구조」로 친다.
   전체 문장의 절반 넘게 고쳤다면 그렇게 고친 이유를 한 줄 덧붙인다 (저자가 다시 쓴 글로 느낄 수 있으므로).

## 5. 판본 변환

- **상세도 변환** (예: 자세히 → 요약판): 결론과 「결정 필요」 문구를 글자 그대로 유지하고 아래만 줄이거나 늘린다. 판본 간 결론이 달라지면 안 된다. 요약판에서 숫자를 뺄 수는 있지만 바꾸지는 않는다.
- **언어 변환** (한국어판 ↔ 일본어판): 직역하지 않는다. 대상 언어 템플릿의 제목·순서로 다시 쓰고, 결론·결정 필요·숫자는 뜻이 같아야 한다. 언어판마다 상세도를 따로 정할 수 있다 (예: 한국어 `detailed` + 일본어 `short`).

## 6. 취향 규칙 (taste)

- 파일: `~/.claude/psedit/taste.md` (스킬 폴더 밖. 스킬을 다시 설치해도 남는다). 없으면 이 절은 건너뛴다.
- 작성·윤문의 마지막 단계에서 읽고 적용한다.
- 사용자가 "이 표현 앞으로 쓰지 마", "이 부분은 이렇게 써", "この言い方はやめて" 같은 지적을 하면 그 자리에서 한 줄 추가하고 추가했다고 한 줄로 알린다. 파일이 없으면 만든다.
  ```
  - [규칙] {쓰지 않을 표현} → {대신 쓸 표현} ({ko|ja}, {YYYY-MM-DD})
  ```
- 같은 방향의 규칙이 3개 쌓이면, 프로젝트에 문체 자동 검사 도구(textlint 등)가 있을 때만 그 도구의 경고 규칙으로 올릴지 사용자에게 묻는다. PSEdit의 안내 훅은 문체를 검사하지 않으므로 여기에 해당하지 않는다.
