# PSEdit 利用マニュアル

## この文書でできること

PSEdit スキルを導入し、Claude Code に日本語・韓国語の文書を書かせたりブラッシュアップさせたりできる。プロジェクトごとに自動案内のオン・オフも決められる。

1. スキルのフォルダを `~/.claude/skills/psedit` にリンクする。
2. どのプロジェクトでも「議事録を書いて」「この設計書をブラッシュアップして」と頼む。
3. 自動案内が要らないプロジェクトには、`.claude/psedit.json` に `{ "hook": "off" }` を置く。

## 始める前に

- Claude Code（デスクトップアプリまたは CLI）
- PSEdit リポジトリを取得したフォルダ（`git clone https://github.com/TaekangKwon/PSEdit.git`）
- Node.js（自動案内フックの実行に使う。フックを使わないなら不要）

手順 1「導入」の PowerShell のコマンドは同じウィンドウで実行する。先に `$repo` にリポジトリを取得したフォルダを入れておく（例：`$repo = "C:\path\to\PSEdit"`）。

## 手順

### 1. 導入

1. スキルのフォルダをユーザーのスキル置き場にリンクする。ディレクトリジャンクション（Windows で、フォルダを別の場所にあるように見せるリンク）でリンクすると、リポジトリのファイルを直した時点で全プロジェクトに反映される。
   ```powershell
   New-Item -ItemType Junction -Path "$HOME\.claude\skills\psedit" -Target "$repo\skills\psedit"
   ```
   macOS・Linux では `ln -s <リポジトリ>/skills/psedit ~/.claude/skills/psedit` でシンボリックリンクを作る。
   - 確認方法：`Test-Path "$HOME\.claude\skills\psedit\SKILL.md"` が `True` を返す。
2. グローバルの `CLAUDE.md` をバックアップする。
   ```powershell
   Copy-Item "$HOME\.claude\CLAUDE.md" "$HOME\.claude\CLAUDE.md.bak_$(Get-Date -Format yyyyMMdd)"
   ```
   - 確認方法：`~/.claude/` に `CLAUDE.md.bak_日付` ができている。
3. 文章ルールをグローバルの `CLAUDE.md` の末尾に追加する。目印のコメントで囲んでおくと、後でその部分だけ探して消せる。
   ```powershell
   $snip = Get-Content -Raw "$repo\install\CLAUDE.snippet.md"
   Add-Content -Encoding utf8 "$HOME\.claude\CLAUDE.md" "`n<!-- psedit:rules -->`n$snip<!-- /psedit:rules -->"
   ```
   - 確認方法：`Select-String -Path "$HOME\.claude\CLAUDE.md" -Pattern "psedit:rules"` が 2 行（開始・終了）を見つける。
4. 自動案内フックを登録する。`~/.claude/settings.json` の `hooks.UserPromptSubmit`（メッセージを送るたびに動くフック）に次の項目を入れる。ほかのフックがすでにあれば、同じ `hooks` 配列に追加する。
   ```json
   "UserPromptSubmit": [
     {
       "hooks": [
         { "type": "command", "command": "node \"$HOME/.claude/skills/psedit/hooks/psedit-prompt.mjs\"" }
       ]
     }
   ]
   ```
   - 確認方法：`node -e "JSON.parse(require('fs').readFileSync(require('os').homedir()+'/.claude/settings.json','utf8'))"` がエラーなしで終わる（JSON が壊れていない）。
5. Claude Code で新しいセッションを開く。スキル・フック・CLAUDE.md はセッション開始時に読み込まれる。
   - 確認方法：どのプロジェクトでも「議事録を書いて」と送ると、Claude が psedit スキルを呼び出し、決定事項から始まる議事録を返す。入力欄に `/psedit` と打って一覧に出るかを見てもよい。

### 2. 文書を新しく書く（作成モード）

1. 文書の種類と材料（事実・数値・決まったこと）を一緒に頼む。スキル名は言わなくてよい。
   ```
   Notion から Confluence への移行の検討資料を書いて。利用者 120 人、Notion は 1 人月 15 ドル、Confluence は 11 ドル、更新日は 12 月 31 日。
   ```
   - 確認方法：文書の先頭に 3 行以内の「結論」、そのすぐ下に「要判断」がある。
2. 分量を決めたいときは、同じ依頼に詳しさの表現を入れる。指定がなければ文書は「普通」になる。

   | 表現（日 / 한） | 詳しさ | 文書の形 |
   |---|---|---|
   | 短く、簡潔に / 짧게, 간단히 | 要約 `short` | 結論・要判断・根拠（1 項目 1 行）だけ |
   | （指定なし）、普通で / 보통으로 | 普通 `normal` | テンプレート全体。詳細は要点だけ |
   | 詳しく、具体的に / 자세히, 구체적으로 | 詳細 `detailed` | テンプレート全体＋例・手順・比較表・理由・よくある質問 |

   - 確認方法：ファイルに保存した文書は、先頭の frontmatter に `detail: <段階>` が書かれる。
3. 結果を読み、「要判断」の項目に答える。作成モードでは、Claude は与えられた事実から必ず推奨案を出す。情報が足りなければ「A を推奨。ただし X なら B」のように条件付きで書く。

文書の種類は依頼の表現で決まる。

| 依頼の表現 | テンプレート | 先頭の節 |
|---|---|---|
| 設計書、方式設計 / 설계서 | `design` | 結論（設計方針） |
| 検討資料、提案書、比較 / 검토자료 | `review` | 結論（推奨案） |
| 調査資料、調査報告 / 조사자료 | `research` | 結論（自分たちにとっての意味） |
| 利用者マニュアル、手順書 / 매뉴얼 | `manual` | この文書でできること |
| 作業報告、進捗報告 / 작업보고 | `report` | 結果 |
| 議事録 / 회의록 | `minutes` | 決定事項 |

「報告書」だけのときは中身で選ぶ。判断を求めるなら検討資料、分かったことを伝えるなら調査資料、進み具合なら作業報告になる。

### 3. 既存の文書を整える（ブラッシュアップモード）

1. ファイルのパスを渡すか本文を貼り付けて、「ブラッシュアップして」「リライトして」「윤문해줘」と頼む。
   ```
   docs/plan/api-design.md をブラッシュアップして
   ```
2. Claude は次の順で直す。構成を先に、文体を後に直す。
   1. 結論が原文のどこかにあれば先頭へ移す。原文が推量で書いた結論は、移した後も推量の表現を 1 つ残す。
   2. 散らばった選択肢・決定事項を「要判断」に集める。原文に推奨がなければ問いだけを書く。
   3. 中身のない書き出し・締め（「〜について解説します」「いかがでしたでしょうか」）と繰り返しを消す。
   4. パターン辞書で文体を直す（立場 → 主体 → 構造 → 語彙 → 記号の順）。
   - 確認方法：直した文章の後に、次の形の報告が付く。
   ```
   構成：4 章に散らばっていた結論を先頭の「結論」に集め、「まとめ」を削除
   文体：16/32
   要確認：Lua スクリプトが 0/1 しか返さないため、X-RateLimit-Remaining の値の出どころが分からない
   ```
3. 報告の「要確認」に答えるか、原文を直す。「結論の候補」が出ていれば、原文に結論がなかったということだ。候補を 1 つ選ぶと、Claude がそれを本文に入れる。

ブラッシュアップは、書き手の文章を書き手の文章のまま残す。事実・数値・否定・条件・時制・確度・単位、コードブロック、表の中のデータは変えない。敬体・常体などの口調もそのまま残す。全体の半分を超える文を直したときは、報告に理由が 1 行付く。

### 4. 別の版を作る

1. 同じ文書の別の詳しさや、別の言語版を頼む。
   ```
   この検討資料の要約版を作って
   이 설계서의 한국어판 만들어줘（자세히）
   ```
   - 確認方法：要約版・詳細版は「結論」と「要判断」の文言が元の文書と一字一句同じ。言語版は直訳せず、対象言語のテンプレートの見出し・順序で書き直す。結論・要判断・数値の意味は元の文書と同じ。

### 5. 自分の好みのルールを残す

1. 結果を読んで気に入らない言い回しがあれば、そのまま伝える。
   ```
   「活用する」は今後使わないで。「使う」にして。
   ```
   - 確認方法：Claude がルールを追加したと 1 行で知らせ、`~/.claude/psedit/taste.md` に次の形の行ができる。
   ```
   - [規則] 活用する → 使う (ja, 2026-11-09)
   ```
2. 以後、Claude はすべての作成・ブラッシュアップの最後の段階でこのファイルを適用する。ルールを消すときは、その行を直接消す。

`taste.md` はスキルのフォルダの外にあるので、スキルを入れ直しても残り、リポジトリにもコミットされない。

### 6. プロジェクトごとの自動案内を決める

1. プロジェクトのルートに `.claude/psedit.json` を作る。
   ```json
   { "hook": "off" }
   ```
   値の意味は「設定項目」の表にある。ファイルがなければ `auto` で動く。
2. 設定をチームで共有するならファイルをコミットする。自分だけで使うならコミットしない。
   - 確認方法：そのプロジェクトで新しいセッションを開き、「議事録を書いて」と送る。`auto`・`always` なら psedit スキルを呼び出す。`off` ならフックの案内なしで処理される（グローバル CLAUDE.md のルールとスキルの説明があるので、スキルが使われることはある）。

### 7. 取り外す

1. リンクを消す。消えるのはジャンクションだけで、リポジトリの元ファイルは残る。
   ```powershell
   cmd /c rmdir "$HOME\.claude\skills\psedit"
   ```
2. グローバルの `CLAUDE.md` から、`<!-- psedit:rules -->` から `<!-- /psedit:rules -->` までを消す。
3. `~/.claude/settings.json` から、`psedit-prompt.mjs` を含むフックの項目を消す。
4. 好みのルールも消すなら、`~/.claude/psedit/` フォルダを消す。
   - 確認方法：新しいセッションで `/psedit` が一覧に出ない。

## 設定項目

### プロジェクト設定 `.claude/psedit.json`

| 項目 | 既定値 | 値と動作 |
|---|---|---|
| `hook` | `auto` | `auto`：依頼に文書のキーワードがあるときだけ案内する。たいていのプロジェクトに合う |
| | | `always`：すべての依頼に案内する。文書だけを扱うリポジトリに合う |
| | | `off`：案内しない。独自の文書ツール・様式だけを使うプロジェクトに合う |

- 作業フォルダから上へたどって、最初に見つかった `.claude/psedit.json` を使う。そのためワークツリー（`.claude/worktrees/…`）では元のリポジトリの設定が適用される。
- `/` で始まるコマンドと、`psedit` を直接書いた依頼には案内を付けない。
- ファイルが壊れていれば `auto` で動く。フックでエラーが起きても依頼は止まらない。
- キーワードの一覧は `skills/psedit/hooks/psedit-prompt.mjs` の `KEYWORDS` にある。例：設計書、仕様書、議事録、ブラッシュアップ、설계서、회의록、윤문。

### 文書の frontmatter

| 項目 | 値 | 説明 |
|---|---|---|
| `detail` | `short` / `normal` / `detailed` | 文書の詳しさ。詳しさを指定すると Claude が書き込む |
| `audience` | `self` / `team` / `stakeholder` / `end-user` | 読み手。`stakeholder`・`end-user` なら専門用語を初出で説明し、数値に「良いのか悪いのか」を添える。なければ文書の種類から推定する（設計書=team、検討資料=stakeholder、マニュアル=end-user、その他=team） |

### ファイルの場所

| 何 | 場所 |
|---|---|
| スキル本体 | `skills/psedit/SKILL.md`（`~/.claude/skills/psedit` にリンク） |
| 文書の骨組み | `skills/psedit/templates/{ko,ja}/{design,review,research,manual,report,minutes}.md` |
| 構成チェック | `skills/psedit/references/structure-checklist.md` |
| 文体パターン辞書 | `skills/psedit/references/patterns-ja.md`、`patterns-ko.md` |
| 自動案内フック | `skills/psedit/hooks/psedit-prompt.mjs` |
| グローバルルールの元 | `install/CLAUDE.snippet.md` |
| 好みのルール | `~/.claude/psedit/taste.md`（最初の指摘のときにできる） |

## 困ったときは

| 症状 | 対処 |
|---|---|
| 文書を頼んだのに psedit スキルが使われない | 依頼に文書の種類（設計書・議事録など）を入れる。それでも使われなければ `/psedit` で直接呼ぶ。導入直後なら新しいセッションを開く |
| フックの案内が入らない | `settings.json` にフックの項目があるか、プロジェクトの `.claude/psedit.json` が `off` でないか、`node` が PATH にあるかを見る。設定を変えた後は新しいセッションを開く |
| 文書と関係ない依頼に案内が付く | キーワードがたまたま入っている。Claude は文書作業でなければ案内を無視する。頻繁に気になるなら、そのプロジェクトを `off` にする |
| 直しすぎる | 依頼に範囲を書く：「構成はそのままで文体だけ整えて」。その場の指示がスキルのルールより優先される |
| 意味や確度が変わった（「〜と考えられる」が「〜だ」に） | 不変条件の違反。その文を元に戻すよう伝える。繰り返すなら、PSEdit リポジトリのパターン辞書に但し書きを足す |
| プロジェクトの文書様式が無視された | プロジェクトの様式が PSEdit のテンプレートより優先されるのがルール。「このプロジェクトの様式で書き直して」と伝え、様式の場所（`_TEMPLATE` など）を示す |
| スキルを直したのに反映されない | ジャンクションなのでファイルはすぐ変わる。開いているセッションは開始時に読んだ内容を使うので、新しいセッションを開く |

## 知っておくこと

### スキルが自動で使われる仕組み

3 つの仕組みが重なっている。上の 2 つはスキルを使うかどうかを Claude が判断し、フックはキーワードがあれば毎回案内を入れる。

| 仕組み | 場所 | 役割 |
|---|---|---|
| スキルの説明 | `SKILL.md` の `description` | 使う場面とキーワードを Claude に伝える |
| グローバルルール | `~/.claude/CLAUDE.md` の `psedit:rules` ブロック | すべてのセッションに「こうした文書は psedit に従う」というルールを入れる |
| 案内フック | `settings.json` の `UserPromptSubmit` | キーワードのある依頼に「psedit スキルを呼ぶ」という案内を付ける。プロジェクトごとにオン・オフできる |

### スキルがしないこと

- 原文・資料にない事実・数値・固有名詞を作らない。
- プロジェクトに独自の文書様式があれば、その構成を上書きしない。結論を最初の節（または最初の段落）に置き、文体をチェックするだけにとどめる。
- README・CHANGELOG・コードコメント・コミットメッセージ・プロンプトファイルにはテンプレートを当てない。

### ルールがぶつかったときの順位

その場のユーザーの指示 ＞ 不変条件（事実・数値・意味を変えない）＞ 好みのルール（`taste.md`）＞ テンプレート・パターン辞書。

## よくある質問

**Q. プロジェクトの `.claude/psedit.json` を `off` にすると、スキルも使えなくなる？**
止まるのはフックの案内だけ。スキルは入ったままなので、「ブラッシュアップして」と頼むか `/psedit` で呼べば使える。

**Q. ほかの人と一緒に使うには？**
各自が PSEdit リポジトリを取得し、手順 1「導入」に従う。プロジェクトごとの設定 `.claude/psedit.json` は、プロジェクトにコミットすれば全員に適用される。好みのルール `taste.md` は個人のファイルなので共有されない。

**Q. 韓国語で頼んで日本語の文書を書かせられる？**
「日本語で書いて」のように言語を指定すればよい。指定がなければ依頼の言語で書き、「チーム共有用」と言えば日本語で書く。
